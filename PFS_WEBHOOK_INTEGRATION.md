# PFS / PDS webhook — integration manual

This document describes the inbound webhook from FS SR's **Modul PDS** (the
Peppol Delivery Service module on the PFS portal) to postar2. It is the
single source of truth for the contract — the route implementation at
[`src/app/api/webhooks/pfs/route.ts`](src/app/api/webhooks/pfs/route.ts) is
written against the spec described here.

The spec follows the FS SR document "Komunikácia medzi PDS a certifikovanými
poskytovateľmi doručovacej služby" — section *"Poskytnutie údajov subjektu
pre poskytovateľa doručovacej služby"*.

> **TL;DR:** PFS POSTs a JSON array of subject records to our endpoint. The
> body is signed with `SHA512(body + secret)` in hex, sent in the
> `X-PDS-Secret` header. We respond with HTTP 200 / 400 / 401 / 500 and a
> body of `{ "Kód": <code>, "Popis": <text> }`.

---

## 1. Endpoint

| Field             | Value                                                          |
| ----------------- | -------------------------------------------------------------- |
| URL               | `https://<your-postar2-host>/api/webhooks/pfs`                 |
| Method            | `POST`                                                         |
| Content-Type      | `application/json` (charset `utf-8`)                           |
| Transport         | HTTPS only — TLS with valid certificate                        |
| Required header   | `X-PDS-Secret` (see §3 below)                                  |
| Request body      | JSON array of subject records (§2)                             |
| Response          | `{ "Kód": int, "Popis": string }` with HTTP 200/400/401/500 (§4)|
| Communication     | Synchronous — provider returns the result of processing        |

The request URL is the value FS SR has registered for our certified
delivery-service provider account on the PFS portal. Every certified
provider has their own URL and their own webhook secret.

---

## 2. Request body

The body MUST be a **JSON array** of one or more subject records. Even when
the array contains a single record, the wrapping array is required.

### 2.1 Per-record schema

| JSON field            | Type                  | Required | Description                                                                                                                                                       |
| --------------------- | --------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `created`             | ISO 8601 timestamp    | yes      | Time the subject record was generated by PFS.                                                                                                                     |
| `dic`                 | string (10 digits)    | yes      | Slovak DIČ (Daňové identifikačné číslo) of the subject. Validated against `^\d{10}$`.                                                                            |
| `legalName`           | string                | no       | Subject's legal name. May be `null`/absent.                                                                                                                       |
| `company_email`       | string                | no       | Subject's email address. If present, postar2 sends a genesis-admin invitation to this address.                                                                    |
| `company_phone`       | string (E.164-style)  | no       | Subject's phone number, e.g. `+421900123456`. May be absent.                                                                                                       |
| `verification_token`  | string (hex, signed)  | yes      | Signed payload `Sign(<provider_DIC> : <subject_DIC>)` produced by the provider's private key. Verifiable against the provider's public key from the SMP. Stored verbatim by postar2. |

## 3. Authentication: `X-PDS-Secret` header

### 3.1 Construction (sender side — PFS)

```
hash = SHA-512(UTF-8(rawBody + webhookSecret))
header = lowercase or uppercase hex string of `hash` (128 chars)
```

- `rawBody` is the **exact** JSON string sent in the HTTP body — byte-for-byte. Any whitespace, key ordering, or encoding change between hashing and sending invalidates the signature.
- `webhookSecret` is the per-URL secret that FS SR communicated to our company out of band (not via this document, not via any HTTP call).
- The hash is **NOT** an HMAC. It's a plain SHA-512 of the concatenation `body + secret`.

### 3.2 Verification (receiver side — postar2)

postar2 reads the `X-PDS-Secret` header, recomputes `SHA512(rawBody + webhookSecret)` for each currently-active secret, and compares **case-insensitively** with constant-time byte comparison (`crypto.timingSafeEqual`).

If any active secret matches → 200/400/500 path. If none match → 401.

### 3.3 Example signing in Node.js

```js
import { createHash } from "node:crypto";

const rawBody = JSON.stringify([{ /* item */ }]);
const webhookSecret = "<the per-URL secret given to you by FS SR>";
const signature = createHash("sha512")
  .update(rawBody + webhookSecret, "utf8")
  .digest("hex");

const res = await fetch("https://postar.app/api/webhooks/pfs", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "X-PDS-Secret": signature,
  },
  body: rawBody,
});
```

### 3.4 Example signing with curl + openssl

```bash
BODY='[{"verification_token":"abc","dic":"1234567890","created":"2026-05-04T12:00:00Z"}]'
SECRET='your-webhook-secret-here'
SIG=$(printf '%s%s' "$BODY" "$SECRET" | openssl dgst -sha512 | awk '{print $2}')

curl -X POST https://postar.app/api/webhooks/pfs \
  -H "Content-Type: application/json" \
  -H "X-PDS-Secret: $SIG" \
  -d "$BODY"
```

### 3.5 Secret rotation

The system_settings key `pfs_webhook_secret` can hold **comma-separated**
secrets to support no-downtime rotation:

```
old-secret-2026-01,new-secret-2026-05
```

postar2 tries each value in order; any match wins. Once you confirm PFS has
cut over to the new secret (audit log will show `WEBHOOK_RECEIVED` events),
remove the old value.

**Storage**:
- Primary: `system_settings.pfs_webhook_secret` (editable by super admin in `/dashboard/settings`)
- Fallback: `PFS_WEBHOOK_SECRET` env var on Vercel (used only when the system_settings row is absent or empty)

## 4. Response

postar2 always returns a JSON body of `{ "Kód": int, "Popis": string }` with
the matching HTTP status code.

| HTTP / `Kód` | `Popis`                                              | When                                                                     |
| ------------ | ---------------------------------------------------- | ------------------------------------------------------------------------ |
| `200`        | `OK`                                                 | All items in the batch were validated, persisted, and audited            |
| `400`        | `Bad Request` (or specific reason)                   | Body wasn't a non-empty JSON array, or any item failed field validation  |
| `401`        | `Missing X-PDS-Secret header` / `Invalid signature` / `Unauthorized` | Header absent, or signature didn't match any active secret  |
| `500`        | `Server error`                                       | Database insertion failed mid-batch; partial commit possible             |

`Popis` is descriptive English text — non-canonical. PFS should switch on
`Kód`, not on `Popis`.

### 4.1 Example success

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "Kód": 200, "Popis": "OK" }
```

### 4.2 Example failure

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json

{ "Kód": 400, "Popis": "Invalid DIC format: must be exactly 10 digits" }
```

## 5. Validation order

postar2 processes the request in this order; a failure at any step ends the
request immediately.

1. **Header check** — `X-PDS-Secret` must be present (else `401`).
2. **Signature verification** — `SHA512(body + secret)` must match (else `401`). Tries every active comma-separated secret.
3. **JSON parse** — body must parse as JSON (else `400`).
4. **Array shape** — body must be a non-empty array (else `400`).
5. **Per-item shape** — each item must be an object with `verification_token` (string), `dic` (string), `created` (string). DIC must match `^\d{10}$`. **All items validated before any DB write** — a malformed item in slot 5 prevents items 1-4 from being committed.
6. **Per-item processing** — see §6.

If a DB error occurs during processing of item N, items 1..N-1 may already
be committed. postar2 logs the error and returns `500`. PFS may safely
retry — the `pfs_verifications` table is append-only and `companies` upsert
by `dic` is idempotent.

## 6. Side effects per item

For each successfully validated item, postar2 performs:

### 6.1 Append raw payload to `pfs_verifications`

```sql
insert into pfs_verifications (
  verification_token, dic, legal_name, company_email,
  company_phone, pfs_created_at
) values (...);
```

This row is the durable record of the inbound webhook call. It is never
overwritten — repeated calls with the same `dic` create new rows. Use this
table for forensic / audit purposes.

### 6.2 Upsert `companies` by `dic`

- If a row with this `dic` already exists → reuse `companies.id`. No fields are updated; the legacy data is preserved.
- Otherwise → insert a new `companies` row with `dic`, `legal_name`, `company_email`, `company_phone`, `pfs_created_at`, and a default `price_per_document = 0.01`.

This means **postar2 treats `dic` as the company identity**. Sending an
updated `legalName` or `company_email` for an existing `dic` does NOT update
the existing row; super admins can edit the company manually if needed.

### 6.3 Audit `WEBHOOK_RECEIVED`

A CEF audit row is written:

```json
{
  "eventId": "WEBHOOK_RECEIVED",
  "eventName": "PFS webhook received",
  "details": {
    "dic": "1234567890",
    "isNewCompany": true,
    "verificationToken": "<full token>"
  },
  "sourceIp": "<inferred from x-forwarded-for>",
  "userAgent": "<inferred from User-Agent header>"
}
```

### 6.4 Genesis-admin invitation (if `company_email` was provided)

- Pre-create a Supabase auth user for `company_email` (idempotent — silently no-ops if the user already exists).
- Insert an `invitations` row with `roles=['company_admin']`, `is_genesis=true`, 48-hour expiry.
- Audit `INVITE_CREATED`.
- Send a transactional email via Resend with the magic-link sign-in URL.

If invitation sending fails (Resend outage, etc.), the failure is logged
and the webhook still returns `200` — the durable artifacts (companies row,
pfs_verifications row, audit log) are already committed.

If `company_email` is absent or empty, no invitation is sent and the
genesis admin must be invited later via the web UI.

---

## 7. Idempotency

- **`pfs_verifications`** is append-only. Two webhook calls with the same `dic` produce two rows.
- **`companies`** upsert is idempotent on `dic`. Two webhook calls with the same `dic` produce one row.
- **`invitations`** is idempotent in the genesis case — `createInvitation` returns `alreadyExists: true` if the recipient is already an active genesis admin of this company. No duplicate invite email sent.

Therefore PFS may safely retry on transient failures (`500` responses,
network timeouts). The only externally-visible non-idempotent side effect
is the email — but Resend itself dedupes immediate duplicates within a
short window, and the magic-link tokens are unique per attempt anyway.

## 8. Non-functional notes

### 8.1 TLS

- HTTPS only. Production deployment is on Vercel with a Let's Encrypt certificate.
- The endpoint will refuse plain HTTP redirects; use the canonical HTTPS URL.

### 8.2 Rate limits

postar2 has no per-source rate limiter on this route. We rely on PFS
sending at human-scale rates (one webhook per company onboarding event).
If volume changes, we'll add a token bucket — please tell us before any
batch >100 items lands.

### 8.3 Downtime notification

Per the spec: if we plan downtime or hit unplanned issues that affect this
endpoint, we MUST notify FS SR so they can mark the URL inactive on their
side. Operational checklist:

- Planned: notify FS SR ≥48 h before any deploy that affects the webhook
  contract or its URL.
- Unplanned: notify FS SR as soon as we detect a multi-minute outage; FS
  SR will pause sends.

### 8.4 Observability

Every webhook call produces:

- A row in `pfs_verifications` (raw payload archive).
- A `WEBHOOK_RECEIVED` audit row (CEF format, partitioned by month).
- Console logs in Vercel with prefix `[PFS webhook]` for failures.

Search the audit log at `/dashboard/audit` filtered by `WEBHOOK_RECEIVED`
to see every call ever received.

## 9. Future hardening (not yet implemented)

### 9.1 SMP-based `verification_token` validation

The spec defines `verification_token` as `Sign(<provider_DIC> : <subject_DIC>)`
using the provider's private key. The signature is verifiable against the
provider's public certificate published in the SMP.

Currently postar2 stores the token but does NOT verify it. Adding
verification would require:

- An SMP client (we don't have one yet) to fetch the provider's public key by DIC.
- A short-lived cache (~24 h) of fetched keys.
- A verify step after signature validation but before DB writes.

This is defense-in-depth — the SHA-512 + secret check is already strong.
File this under "nice to have", not a compliance gap.

### 9.2 Replay protection

We don't currently check `created` against a freshness window or maintain a
seen-set of `(dic, created)` pairs. A stolen-and-replayed webhook would
re-credit the `pfs_verifications` table but the `companies` upsert is
idempotent, so the only side-effect is an extra invitation email if the
recipient hasn't yet accepted. Not a security issue today; would become
relevant if we ever charge per webhook call.

```
URL:      POST https://<host>/api/webhooks/pfs
Header:   X-PDS-Secret: <128-char hex of SHA512(rawBody + webhookSecret)>
Header:   Content-Type: application/json
Body:     [ { verification_token, dic, legalName?, company_email?, company_phone?, created } , ... ]
Success:  200 { "Kód": 200, "Popis": "OK" }

```
